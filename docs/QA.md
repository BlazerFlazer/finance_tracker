# QA Report

This is an honest account of how FinTrack was tested, what was found, what was fixed, and what remains a known gap. Nothing here is aspirational — every "fixed" item was reproduced first, then verified fixed against the running app, not just reasoned about in the abstract.

## Method

Three layers, in this order:

1. **Automated tests** — `npm test` (Vitest): 14 HTTP-level integration tests against the real auth flow (`server/src/http/routes/auth.integration.test.ts`, using Fastify's `app.inject()` — no real network socket), 9 schema tests (constraint/trigger/cascade behavior against a real PGlite instance), 5 i18n parity tests (every key present, with matching placeholders, across all three languages). **28/28 passing**, `tsc --noEmit` clean on both `server/tsconfig.json` and `web/tsconfig.json`, at the time this document was last updated.
2. **Manual, in-browser QA** against the real dev server (`npm run dev`) — not a mock, not a component-level render test. Every page in the sidebar was opened and visually inspected; the higher-risk interactive flows (registration, email verification via the dev mailbox, the debt payoff calculator, CSV import end-to-end including column mapping and undo, the PDF report download, the receipt OCR pipeline, the command palette / global search, admin access control) were exercised by actually driving the UI, not by reading the code and assuming it works.
3. **Source review** triggered by anything that looked even slightly off during manual QA — every bug below was chased from "this looks wrong on screen" to the actual line of code, fixed, and then re-verified live, not just patched blind.

## Bugs found and fixed during this pass

| # | Where | What was wrong | Fix |
|---|---|---|---|
| 1 | Receipt scanner (`web/src/pages/app/ReceiptsPage.tsx`) | **Every OCR scan silently failed.** `tesseract.js` v7's browser feature-detection picked a `-relaxedsimd-` WASM core variant on relaxed-SIMD-capable browsers, but the installed `tesseract.js-core@6` package doesn't ship that variant — every scan threw inside the worker and fell back to "manual entry only", with no visible error explaining why. Found by actually uploading a test image rather than trusting the earlier code-level review of the asset-serving route. | Pin an explicit `.js` core file path (skips the broken auto-detection). Verified against a synthetic receipt image: merchant, date, and amount all now extract correctly. |
| 2 | Same file, `parseReceiptText()` | The date regex assumed `DD/MM/YYYY` unconditionally; a receipt date written `MM/DD/YYYY` (e.g. `09/29/2026`) got reassembled as month = 29, an invalid date the `<input type="date">` silently blanks with no error shown. | Validate the assumed day/month against calendar ranges and swap when only one reading is valid. |
| 3 | Same file | The amount regex matched bare integers, so a 4-digit year in the date line could be picked as the "total" (partially, as a truncated 3-digit match) ahead of the real amount. | Require the 2-decimal component that a real currency amount always has; a bare integer (year, quantity, receipt #) no longer matches. |
| 4 | Monthly review (`web/src/pages/app/ReviewPage.tsx`) | "vs. previous month" divided by `Math.max(1, previousValue)` — when last month's income was genuinely $0, this month's $4,800 divided by $0.01 produced **"+48,000,000%"**. | Show "—" when there's no real previous-period baseline to compare against, instead of a division-by-near-zero artifact. |
| 5 | Same file + `server/src/domain/review.ts` | "Biggest category" showed the raw, untranslated, lowercase `system_key` (e.g. `rent`) for any default category, instead of its localized label. | Pass `systemKey` through alongside `name` and render both with the existing `categoryLabel()` helper (the same one `TransactionsPage` already used correctly). |
| 6 | PDF report (`server/src/reports/pdf.ts`) | Same root cause as #5, in the generated PDF. The PDF generator has no access to the frontend's per-language category catalogue. | Added a capitalize-the-slug fallback (`rent` → `Rent`) — readable, though not translated into RU/UZ; see Known gaps. |
| 7 | Notification settings (`web/src/pages/app/NotificationsPage.tsx`) | Notification types rendered as `type.replace(/_/g, ' ')` — e.g. "upcoming bill" instead of "Upcoming bill", and never translated into RU/UZ at all. | Added `enums.notificationType.*` to all three language catalogues (9 keys × 3 languages) and switched to `t()`. |
| 8 | Security Center (`web/src/pages/app/SecurityPage.tsx`) | Same pattern as #7 for the security-event activity list ("new device login" instead of "New device sign-in", untranslated). | Added `enums.securityEventType.*` to all three catalogues (21 keys × 3 languages) and switched to `t()`. |
| 9 | Privacy Center (`web/src/pages/app/PrivacyCenterPage.tsx`) | The "what's stored" counts showed raw JS property names for two rows — `journalEntries` and `securityEvents` — instead of "Journal entries" / "Security events". The lookup dictionary was keyed in `snake_case`, but the `Db` layer returns every column camelCased regardless of how the SQL aliased it, so the lookup silently missed and fell back to the raw key. | Fixed the dictionary's keys to match what the layer actually returns. |
| 10 | Admin overview (`server/src/http/routes/admin.ts`) | **"Active (30d)" and "New (7d)" could show a higher number than "Total users"** — `totalUsers` excluded demo accounts (`WHERE NOT is_demo`) but `activeUsers`/`newUsers`/`totalTransactions` didn't, so a demo session's own activity inflated numbers meant to describe the real user base. | Applied the same `NOT is_demo` filter to all four stats, consistently. |
| 11 | Global search / command palette (`server/src/http/routes/search.ts`) | Searching for a default category by its displayed name (e.g. typing "rent") returned **zero results**, because the query only matched the `name` column — and a default/template category has `name IS NULL` (only `system_key` set; the label is resolved client-side). Found because the AI assistant correctly reported rent as the largest expense category while the search box couldn't find it at all — a real, previously-invisible inconsistency. | Match `system_key` as well as `name`. Also removed an `as never` type-cheat in `CommandPalette.tsx` that had been silently masking the missing field. |
| 12 | Command palette (`web/src/components/layout/CommandPalette.tsx`) | Typing a query that matched neither a static action nor any search result rendered a totally empty dropdown — no "no results" message. | Added an explicit empty state (`common.noResults`, all 3 languages). |
| 13 | Calendar (`web/src/pages/app/CalendarPage.tsx`) | Day cells had no `aria-label` — a screen reader announced a bare number with no date context. | Added `role="gridcell"` and a full localized date label (e.g. "Tuesday, September 29, 2026 (Today)"); verified via the DOM that every cell now carries it. |

Each fix was verified against the *running* dev server after the change — not just re-read — and `npm test` + `npm run typecheck` were re-run clean after every fix in this table.

## Investigated, found NOT to be a bug

Three separate times during rapid automated screenshot-based testing, a chart appeared completely blank or partially drawn (the mobile sidebar overlay, the debt payoff calculator's line chart, the forecast chart, the money-flow donut). Each was chased down to the DOM/network level rather than assumed broken: in every case the real data and a correctly-shaped SVG path were already present, and the issue was that a screenshot had been taken mid-way through Recharts' default ~1.5s entry animation (or, for the sidebar, one frame before a CSS transition finished). A second screenshot taken a moment later showed the fully-rendered, correct chart every time. No code changes were made for these.

## Areas manually exercised end-to-end and confirmed working

- **Registration → onboarding → email verification**, including: realtime email/username availability checks, the password strength meter and banned-common-password rejection (tested with `password123`, correctly flagged and blocked), password-confirmation mismatch detection, the unchecked-by-default ToS/Privacy checkboxes, the 12-question onboarding wizard, the verification email (retrieved via the dev mailbox at `/api/dev/mailbox` and followed), and the post-verification dashboard unlocking.
- **CSV import**, fully: file parse and column auto-mapping, per-row category mapping, the row preview with per-row selection, commit, the resulting transactions (correct amounts, signs, categories, dates), and **undo** (confirmed it reverses the batch cleanly).
- **Receipt OCR**, fully, post-fix (see bug #1): a synthetic receipt image correctly produced merchant, date, and amount.
- **PDF report generation** — downloads successfully (200 OK, no console errors) for a real period with real data.
- **Command palette / global search (Ctrl+K)** — static actions, live search across transactions/accounts/categories/goals/subscriptions/debts, and the empty state (post-fix).
- **AI assistant** — confirmed it answers from the user's own data and, with no `ANTHROPIC_API_KEY` configured in this environment, correctly falls back to its deterministic rule-based engine rather than failing — exactly the required "AI is optional" behavior.
- **Admin panel access control** — a non-admin account is blocked both from the nav (not shown) and from the route directly (`/app/admin` → "You don't have permission to do that"); a promoted admin account sees Overview/Users/Security events and the numbers are now internally consistent (see bug #10).
- **Security Center** — 2FA setup is correctly blocked for demo accounts with a clear inline message; session list, device list, and (post-fix) the security-activity feed.
- Every other sidebar page — Calendar, Transactions, Accounts, Categories, Recurring, Budgets, Goals & savings, Subscriptions, Debts (+ payoff calculator), Analytics, Net worth, Forecast, Money simulator, Where did my money go, Spending heatmap, Timeline, Monthly review (post-fix), AI insights, Financial health, Journal, Notifications (post-fix), Privacy center (post-fix), Settings — opened, visually inspected, and populated correctly against real seeded and freshly-created data.
- **Mobile layout** (375×812 emulation) — hamburger sidebar open/close, bottom nav, stacked cards.
- Light/dark theme toggling.

## Known gaps

These are real, deliberately-scoped limitations — not things believed fixed. None of them are security issues or functional blockers; a user can complete every core task without hitting one.

- **Default-category names aren't localized into RU/UZ in two secondary surfaces**: the PDF report (falls back to a capitalized English slug, e.g. "Rent", rather than "Аренда"/"Ijara") and the search index (matches the English `system_key`, so an RU/UZ speaker searching in their own language won't find a *default* category by its translated name — a custom-renamed category is unaffected, since it has a real `name`). The primary UI surfaces (transaction lists, budgets, analytics, the review page) all resolve and translate the label correctly.
- **Notification email bodies are English-only** regardless of the recipient's UI language (the notification *type label* shown in-app is now fully localized, per fix #7 — this gap is specifically about the templated email text sent for a triggered notification).
- **Onboarding step "Your spending"** requires answering the two yes/no questions before "Next" proceeds, but the button doesn't visually indicate it's disabled while they're unanswered — clicking it silently does nothing rather than showing a validation message. Every other step's disabled state is visually obvious (grayed out); this one specifically looks identical whether enabled or not.
- **Budgets have create and delete, but no dedicated edit UI** — changing a budget's amount currently means deleting and re-creating it.
- **A goal's "required monthly" contribution is shown in a raw `"478 USD/mo"` format** rather than through the app's own `<Money>` formatting component used everywhere else.
- **No formal accessibility audit was run in this pass** (no axe-core pass, no dedicated screen-reader/keyboard-navigation sweep) — pages use semantic HTML, labeled form fields, and visible focus states throughout, but this hasn't been verified against WCAG criteria specifically. This is the one item on this list that's an honest "not yet checked" rather than "checked and found small" — treat accessibility as unverified, not as confirmed compliant. (One concrete gap this kind of sweep would likely have caught, the Calendar's missing day-cell labels, was found incidentally and fixed — see #13 above; there are almost certainly others like it not yet found.)

## Test data note

The demo account (and the two accounts created fresh during this QA pass) use randomized seed data — merchant names, categories, and amounts differ between demo sessions by design, so exact figures in this document (e.g. specific dollar amounts) reflect what was on screen at the time of testing and won't reproduce identically on a fresh demo session.
